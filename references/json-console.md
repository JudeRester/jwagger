# JSON 명세와 콘솔 구현 규약

로컬 Python 콘솔을 만들거나 수정할 때 적용한다. 새 콘솔에는 Python 3 표준 라이브러리를 사용한다. 호환 실행기가 있으면 기존 명세와 지원하는 인증 방식·단언을 먼저 확인한다. 아래 파일명은 새 콘솔의 기본값이다.

| 파일 | 내용 |
|---|---|
| `cases.json` | `cases`와 필요할 때 `sessionCheck`를 담는 객체 |
| `fixtures.json` | 확인된 개발 데이터 및 확인 근거. 미확인 값은 `""` |
| `run_api_tests.py` | JSON 로드, HTTP 전달, 판정, 케이스별 결과 관리 |
| `console.html` | 케이스 선택·실행·결과 표시. 케이스별 상수나 판정 분기를 넣지 않는다. |

## 케이스 형식

동일한 엔드포인트의 케이스도 별도 `id`와 단언을 둔다. 아래 예시는 테스트 계정의 호출 주체를 확인한 뒤 알려진 리소스 한 건을 조회한다. 경로, 응답 필드와 인증 확인 방법은 대상 API에 맞춘다.

```json
{
  "sessionCheck": {
    "source": ["호출 주체 조회 API 계약"],
    "request": {"method": "GET", "path": "/api/me"},
    "expect": {
      "status": 200,
      "bodyType": "object",
      "checks": [
        {"op": "equals", "at": ["id"], "value": {"fixture": "SUBJECT_ID"}}
      ]
    }
  },
  "cases": [
    {
      "id": "resource-read",
      "purpose": "알려진 리소스가 반환되는지 확인",
      "source": ["리소스 조회 API 계약"],
      "effect": "read",
      "request": {
        "method": "GET",
        "path": "/api/resources/example"
      },
      "requestNeeds": [],
      "expectNeeds": ["RESOURCE_ID"],
      "controlId": null,
      "expect": {
        "status": 200,
        "bodyType": "object",
        "checks": [
          {"op": "equals", "at": ["id"], "value": {"fixture": "RESOURCE_ID"}}
        ]
      }
    }
  ]
}
```

`id`는 고유 문자열, `purpose`는 문자열, `source`는 소스 경로·메서드·mapper 또는 계약 위치의 배열이다. `effect`는 `read` 또는 `write`, `controlId`는 정상 대조 케이스의 ID 또는 `null`이다. 정상 대조에는 같은 세션에서 실제 정상 레코드를 확인하는 `read` 케이스를 지정한다. `fixtures.json`의 `values`에는 값, `evidence`에는 키별 출처·환경·날짜를 둔다. `{"fixture":"KEY"}`는 `values.KEY`를 참조한다. `requestNeeds`와 `expectNeeds`는 각 구역에서 참조하는 키의 배열이다. 로드 시 스키마에 없는 필드 및 연산, 잘못된 타입, 누락 키, 중복 ID, 존재하지 않거나 순환하는 대조 ID를 설정 오류로 표시한다. 실행기가 일부 연산만 제공하면 지원하지 않는 연산도 로드 단계에서 거부한다.

`request`는 `method`와 `path`, 선택 필드 `query`, `form` 또는 `json`을 받는다. `form`과 `json`은 동시에 선언할 수 없다. JSON 본문은 `null`, `[]`, `{}`, 누락 필드를 그대로 보낸다. 쿼리·폼 값은 API 계약에 맞는 문자열 또는 반복 키를 뜻하는 비어 있지 않은 문자열 배열로 선언한다. `{"tag":["a","b"]}`는 `tag=a&tag=b`, `{"tag":""}`는 `tag=`, 키를 생략하면 전송하지 않는다. `[]`와 `null`의 별도 표현은 API가 정의한 문자열·필드명으로 명시한다. 예를 들어 계약이 문자열 `[]`를 받으면 `{"tag":"[]"}`를 선언한다. 실제 빈 배열이나 `null`을 쿼리·폼 값으로 선언하면 오류로 처리한다. `urlencode(..., doseq=True)`가 빈 배열을 조용히 생략하기 전에 검사한다.

`expect`는 `status` 정수, `bodyType` 문자열, `checks` 배열로 구성한다. `bodyType`은 JSON `array`, `object`, `string`, `number`, `boolean`, `null`과 원문 `text`, 0바이트 `empty` 중 하나다. JSON 본문은 파싱과 타입 확인을 모두 거친다. `""`(JSON 문자열), `null`, `[]`, `{}`, 0바이트를 각각 판정한다. 타입 확인과 `equals`·`row`·`empty` 값 비교에 같은 JSON 타입 규칙을 사용한다. 배열과 객체는 내부 값까지 비교하고, `true`와 `1`, 숫자 `1`과 문자열 `"1"`은 서로 다르다. 호환 입력을 허용하는 계약이라면 허용 값을 명세에 명시한다.

| `op` | 필드와 판정 |
|---|---|
| `equals` | `at`, `value`. 경로에 값이 있고 JSON 타입과 값이 일치해야 한다. |
| `exists`, `absent` | `at`. 경로에 값이 있는지 확인한다. 값이 `null`인 필드도 존재한다. |
| `length` | `at`, `value`(0 이상 정수). 배열의 요소 수, 객체의 키 수 또는 문자열 길이가 일치해야 한다. |
| `keys` | `at`, `allowed`(문자열 배열). 대상은 객체이며, 모든 실제 키가 목록에 있어야 한다. 필수 키는 `exists`로 지정한다. |
| `nonEmpty` | `at`. 값은 있어야 하며 공백만 있는 문자열, `null`, 빈 배열·객체는 실패다. 숫자 `0`과 `false`는 값이 있다. |
| `empty` | `at`, `values`(허용할 JSON 값 배열), 선택 `allowMissing`(기본 `false`). 값 또는 명시적으로 허용한 누락이 일치해야 한다. |
| `row` | `at`, `by`(객체의 키), `value`, `checks`. 대상 배열에서 키가 있고 값이 같은 객체가 정확히 한 개 있어야 한다. `checks`는 해당 행 기준 상대 경로로 평가한다. |
| `rawExcludes` | `value`(비어 있지 않은 문자열). 응답 원문과 파싱한 JSON의 키·문자열 값에서 해당 문자열의 부재를 확인한다. 이렇게 이스케이프된 문자열도 검출한다. |

`at`은 문자열 키 또는 0 이상 정수 인덱스의 배열이다. `[]`는 현재 검사 대상의 루트다. 경로가 없으면 내부 누락 값으로 처리한다. `at` 이외의 기대값 위치에 픽스처를 참조할 수 있다. 비교 대상 픽스처가 `""`면 해당 단언은 미검증으로 기록하고 비교 함수에 넘기지 않는다. `rawExcludes`의 리터럴 `""`는 설정 오류다.

## 실행과 판정 순서

1. 클라이언트가 요청 필수 값과 인증 준비 상태를 확인한다. 세션 확인이 필요한 케이스는 같은 자격 증명으로 `sessionCheck`가 통과한 뒤 실행한다.
2. `controlId`가 있으면 같은 실행의 동일한 대상·인증·픽스처로 정상 대조를 먼저 실행한다. 대조가 `FAIL`·`미검증`·연결 실패면 종속 케이스 결과는 `대조 실패/미검증`이며 본 요청은 보류한다. 대조 중 인증 만료는 `인증 오류`다. 대조의 결과와 보류된 케이스는 별도 행으로 보여 준다.
3. 본 요청의 인증 오류와 연결·수신 오류를 먼저 판별한다. 응답 상한보다 1바이트 더 읽어 잘림을 검출하고, 읽기 예외와 본문이 있는 응답의 `Content-Length` 불일치도 확인한다. HEAD·204·304처럼 본문이 없는 응답은 해당 HTTP 규칙을 적용한다. 압축 응답은 길이 확인 뒤 해제하거나 `Accept-Encoding: identity`를 사용하고 지원하지 않는 인코딩을 오류로 처리한다. 잘린 본문은 일부가 유효한 JSON이어도 판정하지 않는다. 원문을 표시할 때는 수신한 부분임을 명시한다.
4. 완전한 응답의 `status`·`bodyType`을 확인하고 준비된 단언을 실행한다. 확정 불일치는 `FAIL`이다. 통과하지 않은 단언이 없고 미확인 기대값이 남아 있으면 `미검증`, 모든 단언을 확인했으면 `PASS`다.

## HTTP 전달과 인증

1. Python 서버는 `127.0.0.1`에만 바인딩한다. 시작 시 승인된 개발 대상의 `--target`을 `https` scheme, hostname, 유효 포트로 정규화해 origin을 고정한다. URL에 사용자 정보·쿼리·fragment·루트 이외 경로가 있으면 거부한다. 케이스 `path`는 `/` 하나로 시작하는 경로로 제한한다. `//host/x`, URL 전체, 백슬래시, 제어 문자·공백, 쿼리·fragment는 거부한다. 경로를 퍼센트 디코딩했을 때 위 제한을 우회하거나 `.`/`..` 경로 요소가 생기는 값도 거부한다. 고정 origin 뒤에 검증된 경로와 별도 인코딩한 쿼리를 붙이고, 최종 URL을 다시 파싱해 scheme·hostname·유효 포트가 고정 origin과 일치할 때만 인증 헤더를 붙인다. `urljoin`으로 케이스 경로를 붙이지 않는다.
2. 브라우저는 케이스 ID와 선언된 입력만 넘긴다. 서버는 로드한 케이스에서 목적지 경로와 HTTP 메서드를 얻는다. 모든 로컬 요청에 실제 루프백 `Host`를, 실행·인증 등록·리로드 등 POST에는 정확한 루프백 `Origin`도 요구한다. 누락·불일치한 POST를 거부하고 CORS를 열지 않는다. 로컬 페이지와 API 응답에 `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`와 실제 타입의 `Content-Type`을 설정한다. HTML에는 CSP를 적용한다. 예를 들어 스크립트와 CSS를 같은 origin의 파일로 제공한다면 `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'`을 쓴다. `purpose`, `source`, `evidence`, `Location`, 요청·응답·오류는 모두 `textContent`나 텍스트 노드로 그린다. 업스트림 본문·헤더를 로컬 문서의 HTML이나 헤더로 그대로 전달하지 않는다.
3. 시작할 때마다 예측하기 어려운 `instance_id`를 발급한다. 브라우저는 자격 증명 없이 `GET /api/context`로 `instance_id`·고정 origin·`fixture_epoch`를 받아 대상 origin을 표시한다. 사용자가 등록한 자격 증명은 그 컨텍스트와 함께 `POST /api/auth`에 한 번만 보낸다. 쿠키 방식은 `Cookie`와 대상이 요구하는 CSRF 값을 받는다. 서버는 컨텍스트가 현재 값과 정확히 맞을 때만 자격 증명을 메모리에 등록하고, 현재 인스턴스·origin·`auth_generation`에 묶인 임의의 인증 핸들을 반환한다. 이후 실행에는 핸들만 전송한다. 서버는 매 실행에서 이 바인딩을 확인하고 인증 교체·삭제 시 이전 핸들을 폐기한다. 재시작·대상 변경·컨텍스트 불일치 시 이전 입력과 핸들을 지우고 새 등록을 요구한다.
4. 실제 세션을 확인해야 하는 세트는 `sessionCheck`를 선언한다. `request`에는 현재 호출 주체를 반환하는 읽기 요청을 쓰고, `expect`에는 권한 판정에 필요한 주체와 소속 또는 권한 범위를 단언한다. 요청이 보낸 주체 ID를 그대로 돌려주는 경로는 세션 확인에 쓸 수 없다. 인증 등록과 인증 케이스 실행 시작 시 현재 픽스처로 확인한다. 검증할 경로나 기대값이 없으면 실행 준비 부족으로, 주체 또는 권한 범위가 다르면 세션 불일치로 표시하고 종속 케이스를 보류한다. 픽스처 리로드가 성공하면 인증값을 유지하고 세션 확인·대조·현재 결과를 무효화한다.
5. 자격 증명 원문은 파일·환경 변수·명령행·브라우저 저장소·로그에 적지 않는다. 입력 자동완성을 끄고 등록 뒤 입력란을 지운다. 새로고침이나 탭 종료 뒤 핸들을 복구하지 않는다. 사용자가 인증을 지우면 서버의 자격 증명도 폐기한다. `HTTPRedirectHandler`에서 자동 리다이렉트를 차단하고 `HTTPError`에서도 상태·헤더·본문을 읽는다. 의도하지 않은 로그인 리다이렉트, 세션 만료, CSRF 오류는 대상의 응답 계약에 따라 구분한다. 계약상 차단을 나타내는 `403`도 필요한 정상 대조를 확인한 뒤 판정한다. 자격 증명 없는 `401`을 확인하는 케이스를 실행기가 지원하면 `auth: "anonymous"`와 `expect.status: 401`을 선언하고 자격 증명을 보내지 않는다. 익명 케이스는 인증 케이스의 정상 대조로 쓰지 않는다.
6. 직접 연결이 필요한 대상에는 `ProxyHandler({})`를 적용한다. 기본 TLS 설정은 `ssl.create_default_context()`를 사용한다. 개발 CA가 필요하면 해당 신뢰 설정을 지정한다. 레거시 인증서 호환 설정이 필요한 경우 확인한 개발 origin에만 적용하고 호스트 이름과 인증서 체인 검증을 유지한다. 연결 오류에는 TLS·DNS·타임아웃 등 확인한 원인을 표시한다.

## 리로드와 상태 변경 실행

1. 전체·단건 실행, 인증 교체·삭제, 설정 리로드는 서버 상태를 공유한다. 서버의 동일한 잠금으로 실행 시작·상태 변경을 직렬화한다. 실행 중 들어온 다른 실행·리로드·인증 변경에는 `409`를 반환한다. 브라우저 버튼 비활성화는 화면 편의로 제공한다. 잠금 안에서 실행 시작 시 설정·인증 스냅샷과 고유 `run_id`를 확정하고, 네트워크 처리가 끝나면 잠금 안에서 결과를 반영한다.
2. `fixture_epoch`는 설정 로드 성공 시에만 증가시키고 `auth_generation`은 인증 교체·삭제 시 바꾼다. 브라우저 명령에는 확인한 `instance_id`와 `fixture_epoch`를 포함한다. 서버는 오래된 명령을 거부한다. 실행 시작 시 브라우저에 실행 식별값을 알려 준다. 결과 반영과 화면 갱신은 `(instance_id, fixture_epoch, auth_generation, run_id)`가 현재 실행과 일치할 때만 한다. 실패한 리로드는 기존 설정과 epoch를 유지한다. 성공한 리로드는 완료한 실행의 기록을 과거 결과로 남기고, 새 실행에 기존 대조를 재사용하지 않는다.
3. HTTP 메서드와 관계없이 실제 부작용이 있는 케이스에는 `effect: "write"`를 사용한다. 조회용 POST처럼 소스로 읽기 전용이 확인된 요청은 `read`로 지정할 수 있다. 전체 실행과 실패 행의 즉시 재실행은 `read`에 한정한다. 상태 변경은 권한이 확인된 개발 환경에서 변경 대상과 실제 요청값을 표시하고, 사용자가 해당 케이스를 의도적으로 단건 실행할 때만 보낸다.
4. 응답을 잃은 상태 변경은 `변경 결과 불명`으로 기록한다. 타임아웃·중단·연결 단절이나 커밋 여부가 불명확한 5xx 뒤에는 자동 재전송과 재실행 버튼을 막는다. 읽기 전용 조회로 고유한 작업 식별자나 레코드의 변경 상태를 확인하고, 미반영이 확인되면 사용자가 다시 실행할 수 있다. API가 멱등 키의 중복 방지를 보장하면 기존 키·요청 본문을 그대로 재사용하는 재시도도 가능하다. 재시작 등으로 이전 시도를 알 수 없는 경우에는 해당 변경을 보내기 전에 읽기 전용 조회로 같은 작업이 이미 반영됐는지 확인한다. 반영 여부를 확인할 수 없고 멱등 재시도도 안전하게 할 수 없으면 요청을 보류한다.

## 개발자가 돌리는 순서

1. Windows에서는 `py -3 -X utf8 .\run_api_tests.py --target https://<개발-호스트> --port 8766` 같은 시작 명령을 안내한다. 설정은 UTF-8로 읽는다. 화면에 대상 서버와 실제 루프백 주소를 표시하고 준비할 픽스처와 필요한 인증 등록 방법을 안내한다. 픽스처는 허용된 대상 환경에서 준비한다.
2. 실행 전 목록과 상세에 케이스 ID, 메서드·경로·입력, 통과 기준을 보여 준다. 요청과 판정에 필요한 값이 부족하면 해당 키를 별도로 표시한다. 읽기 케이스는 전체 실행과 단건 재실행을 제공한다. 단건 재실행은 이전 응답을 사용하지 않으며 필요한 세션 확인과 대조를 새로 수행한다. 같은 HTTP 요청을 쓰더라도 케이스별 판정을 표시한다.
3. `FAIL` 필터와 별도의 인증·연결/미검증 상태를 제공한다. 상세와 실행별 진단 로그에서 케이스 ID, 실제 요청의 메서드·대상·헤더·쿼리/본문, 응답 상태·헤더·본문, 시간, 기대/관측 값, 실패 단계와 이유를 확인할 수 있게 한다. `Cookie`, `Set-Cookie`, CSRF, 인증 토큰은 항상 가린다. 케이스의 선택 필드 `redact`는 `query`·`form`의 키 배열과 `requestJson`·`responseJson`의 `at` 경로 배열을 받는다. 화면·로그·내보내기 전에 적용한다. 원문에서 민감값을 안전하게 제거할 수 없으면 해당 원문을 숨긴다. 문제가 보고되면 접근 가능한 실행 ID나 로그 경로로 실패 당시의 HTTP 교환을 먼저 확인한다. 재실행 후에도 이전 실패 시도의 관측값과 현재 실행을 구분해 비교할 수 있게 한다.
4. 콘솔의 요청과 판정은 로컬 모의 서버로 검증할 수 있다. 변경한 동작에 맞춰 입력 인코딩과 응답 수신, 세션·대조 실패 시 요청 보류, 오래된 실행 명령 거부, 상태 변경 재전송 방지 등을 확인한다. 실제 대상에서 얻은 응답과 콘솔을 대상으로 한 모의 검증은 구분해 보고한다.
